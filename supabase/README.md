# Supabase — Phase 2B

**Applied.** All 7 migrations below are live on a dedicated project named
"Perkasa Motors Website" (separate from the pre-existing "Perkasa Motors"
project in the same org, which hosts an unrelated internal tool and was
deliberately left untouched — see the Phase 2B chat summary for why).
`seed.sql` has also been run against it — 6 vehicles, matching
`lib/mock/vehicles.ts` exactly. The public vehicle read path in
`lib/data/vehicles.ts` reads from this project; nothing else has been cut
over yet (see that file's header comment for the admin-functions scope
decision).

No `config.toml` is included — that's generated by `supabase init`, which
also depends on the installed CLI version's schema. Run `supabase init` in
this directory (it will detect and keep the existing `migrations/` folder)
before linking the CLI locally to the project, rather than trusting a
hand-written config file to match whatever CLI version is in use.

## What's here

```
supabase/
  migrations/
    20260814030000_enums.sql                    — 11 enum types, ported from lib/types/*.ts
    20260814030100_tables.sql                   — profiles, vehicles, vehicle_media, leads, content
    20260814030200_indexes.sql                  — all indexes not already covered by a UNIQUE constraint
    20260814030300_functions_and_triggers.sql   — updated_at maintenance, profile-on-signup, RLS helper functions
    20260814030400_rls_policies.sql             — row level security for every table
    20260814030500_storage_buckets.sql          — vehicle-media, content-thumbnails buckets + object policies
    20260814041847_fix_set_updated_at_search_path.sql — hardening follow-up, see below
  seed.sql                                      — 6 development vehicles, matches lib/mock/vehicles.ts
```

Applied in filename order — later files depend on enums/tables/functions
from earlier ones (e.g. the RLS migration calls `public.is_active_staff()`,
defined in the functions migration).

The last migration exists because Supabase's own security advisor flagged
`set_updated_at()` for a mutable `search_path` after the first six were
applied — a real, zero-risk hardening fix, applied and then folded back
into this migration history so the repo matches what's actually live.

## To link the CLI to this project locally

```bash
supabase init                              # only if supabase/config.toml doesn't exist
supabase link --project-ref itjytnbipxaflnaplwpd
supabase db pull                           # reconciles local migration history with what's already applied
```

Get the anon/publishable key and project URL from the Supabase dashboard
(Project Settings → API) — never from this repo, and never from chat.

## What's still deliberately not here

- **Vehicle photography.** `vehicle_media` is empty. Uploading into the
  `vehicle-media` bucket requires an authenticated staff session (the
  bucket's write policy is staff-only, by design) — no admin auth exists
  yet, so there's no safe way to upload from this phase without either a
  staff account or the service-role key, both out of scope. Vehicle
  cards/gallery already render correctly with zero media.
- Any `SUPABASE_SERVICE_ROLE_KEY` usage, anywhere. Admin write paths and
  auth are later phases.
- Any change to `lib/data/leads.ts` or `lib/data/social-content.ts` — both
  still read from `lib/mock/`, untouched in this phase.
- The three admin-only functions in `lib/data/vehicles.ts`
  (`getAllVehiclesForAdmin`, `getVehicleByIdForAdmin`,
  `getAllVehicleMediaForAdmin`) — still mock, for the same reason: the
  anon key can never see DRAFT/unpublished rows, so swapping them now
  would make `/admin/inventory` silently show an incomplete list.
