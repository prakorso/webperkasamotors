Perkasa Motors — Stock Number Production Hygiene Audit (Phase 1.5)

Audit only. Nothing was modified: no application code, row, function, trigger, sequence, pool entry, Finance data or production setting. Only SELECTs, schema/function inspection and code/git reading were used. Verdict: **UNSAFE — the next real CAR would receive QA-PAGN-03.**

A. Executive summary
Stock numbers are generated by the database function generate_stock_number(vehicle_type), called by the admin "create vehicle" action. The function prefers a pooled (previously released) number over the sequence, picks the alphabetically first one for the vehicle type, and validates nothing about its format. The pool (stock_number_pool) holds 13 rows, all CAR, all QA/test names (QA-PAGN-03/04/05, QA-T1-*, TEST-PAGN-*). They entered the pool because the delete trigger releases the stock number of any deleted DRAFT/AVAILABLE/ARCHIVED vehicle without checking its format, and those test vehicles were inserted directly into the database (never through the generator) and later hard-deleted. Reproducing the generator's exact selection read-only returns QA-PAGN-03 for CAR and, for motorcycles (empty pool), MOT-0013. No real inventory depends on the 13 pooled numbers. The safest long-term policy is to never reuse stock numbers; an immediate data-only mitigation exists (below) and should happen before any new car is created.

C. Current stock-number architecture
- Tables: public.vehicles.stock_number (text NOT NULL, constraint vehicles_stock_number_key UNIQUE; no CHECK on format) and public.stock_number_pool (id uuid PK, vehicle_type, stock_number text UNIQUE, released_at). RLS is enabled on the pool with no policies, so the API cannot touch it directly; only the two SECURITY DEFINER functions do. No other table or view in the website database uses stock_number.
- Sequences: car_stock_number_seq (last_value 8, is_called true → next 9) and motorcycle_stock_number_seq (last_value 12, is_called true → next 13).
- Functions/triggers: generate_stock_number(vehicle_type) (SECURITY DEFINER; EXECUTE for authenticated, not anon), vehicles_before_delete() + trigger vehicles_before_delete (BEFORE DELETE), vehicles_status_lifecycle, vehicles_set_updated_at.
- Application: lib/actions/vehicles.ts createVehicle calls supabase.rpc("generate_stock_number", { v_type }), then inserts the returned value as stock_number (status DRAFT, unpublished). The app never validates the returned format. Updates never include stock_number (the form says the number is created automatically and does not change). deleteVehicle refuses RESERVED/SOLD (and anything with RESERVED/SOLD history) and otherwise hard-deletes, relying on the trigger to release the number. The admin delete confirmation tells staff the number can be reused.
- Flow: admin creates vehicle → server action → RPC generate_stock_number → pooled number if one exists for that type, else nextval() → INSERT into vehicles.
- Migrations: 20260815050000 (generator + sequences), 20260816010000 (pool, delete trigger, reuse), 20260816020000 (normalised legacy PM-/MP- prefixes to CAR-/MOT- keeping the number, advanced sequences), 20261001010000 (lifecycle: sold_at, status history, history-based delete lock).

D. Production numbering patterns
From the live 18 vehicles: cars CAR-NNNN (width 4), motorcycles MOT-NNNN (width 4); numbering is per type (separate sequences, CAR-0001… and MOT-0001…); the prefix always matches vehicle_type. Legacy PM-000x/MP-000x rows from the seed were renamed in place preserving the digits, so gaps exist and are expected (cars: 0005 absent; motorcycles: 0002–0004 absent). SOLD units keep their numbers permanently (the delete lock). Deleted DRAFT/AVAILABLE/ARCHIVED units release theirs.

I. Reuse-pool structure
stock_number_pool(id, vehicle_type, stock_number UNIQUE, released_at). Enters: only via vehicles_before_delete() (INSERT … VALUES (old.vehicle_type, old.stock_number)), with no format, prefix, namespace or environment check. Leaves: only via generate_stock_number() (selected ORDER BY stock_number ASC FOR UPDATE SKIP LOCKED LIMIT 1, then deleted). Type is stored and matched; duplicates are prevented by the UNIQUE constraint only. released_at is not used for ordering. No other consumer.

J. generate_stock_number logic
For a car: 1) look in the pool for the alphabetically first CAR row (database collation en_US.UTF-8) with a lock; 2) if found, delete it from the pool and return it as is; 3) otherwise nextval(car_stock_number_seq) and return 'CAR-' || lpad(n, 4, '0'). For a motorcycle: the same with MOTORCYCLE and MOT-. The pool is always preferred over the sequence; prefix/format is never validated; test and QA names are fully allowed; only the matching vehicle type is considered; fallback is the sequence. Alphabetical ordering puts QA-PAGN-03 first among all 13 (order: QA-PAGN-03 < 04 < 05 < QA-T1-AVAIL-A < … < TEST-PAGN-05), so the next 13 cars would receive these names in that order before CAR-0009 is ever minted.

K. Deletion/release behavior
- Deleting a DRAFT, AVAILABLE or ARCHIVED vehicle (admin "Hapus permanen" or SQL) releases its number into the pool, whatever its format and whether or not it was ever published.
- A SOLD or RESERVED vehicle, or one whose status history shows it was ever SOLD/RESERVED, cannot be deleted (application check and database trigger), so a historically sold number is never released today. SOLD is final in the owner UI (ALLOWED_TRANSITIONS has no exit), so a sold unit cannot be made deletable through the UI. Before the lifecycle migration the lock checked only current status, so a SOLD→AVAILABLE→delete path existed historically.
- Published numbers are reusable: an AVAILABLE published vehicle can be deleted and its number reissued. Archiving does not release a number.
- Deleting QA/test rows releases their names just like real ones (that is how all 13 got into the pool).

L. Current next CAR number
**QA-PAGN-03.** Evidence: the generator's own query (select stock_number from stock_number_pool where vehicle_type='CAR' order by stock_number asc limit 1) returns QA-PAGN-03 on the live database (13 CAR rows in the pool). If the pool were empty it would mint CAR-0009.

**MOT-0013.** Evidence: 0 MOTORCYCLE rows in the pool; motorcycle_stock_number_seq last_value 12, is_called true.

N. Analytics impact
Marketing Analytics V1 joins GA4 item_id to vehicles.stock_number. Reuse makes the number a non-permanent identity: a future vehicle assigned a released number would inherit the old vehicle's historical GA4 views/clicks; the current mitigation (ignore analytics dated before the vehicle's created_at) only works at day granularity and cannot split a same-day reuse. The QA numbers make it worse: a real car numbered QA-PAGN-03 would carry that name into GA4 events and the QA- exclusion rule the dashboard plans to use, hiding a real vehicle. Risk: **MEDIUM**.

O. Finance impact
Finance is a separate Supabase project and out of scope; read-only schema inspection only. No column anywhere in the Finance public schema (including backups and views) is named or typed like a stock number, slug, vehicle id, website or external key. So there is no database-level link from Finance to website stock numbers. Not verified: manual or spreadsheet-based mappings (for example by plate number) outside the database. Risk: **LOW** at database level; external mappings not verified.

P. Root cause
Three compounding gaps: (1) test vehicles were inserted with hand-made stock numbers outside the generator; (2) the delete trigger releases any deleted non-locked vehicle's number into the pool without validating its format; (3) the generator hands pooled numbers out first, without validating them either. There is no CHECK constraint on vehicles.stock_number to stop non-standard values at insert time, and the pool was never cleaned after the QA cleanups of 18–19 August.

Q. Production risk
High and immediate for inventory identity: the next real car created in the admin is numbered QA-PAGN-03 (then QA-PAGN-04, -05, QA-T1-…, TEST-PAGN-…), shown to customers on the public detail page and sent to GA4/Meta as item_id. Motorcycles are unaffected. A published AVAILABLE vehicle (including QA-PAGN-02) can still be deleted and add another non-standard name.

R. Recommended policy
**Option A — never reuse stock numbers.** Compared: B (reuse only production-format numbers) still allows an identity to be reissued, breaking analytics and audit trails; C (reuse only if never published/never sold) is safer but still reissues numbers that appeared in drafts, URLs, GA4, photos or conversations; D (keep reuse, exclude test namespaces) fixes only today's symptom. Option A keeps identity stable, auditable and compatible with analytics and Finance; its only cost is permanent gaps in the sequence (already present), which the brief says not to optimise. Keep vehicles.id (UUID) as the permanent internal identity and stock_number as the human-readable operational label.

Add to A or B: a CHECK (stock_number ~ '^(CAR|MOT)-[0-9]{4}$') created NOT VALID so only new rows are checked (the two existing QA-PAGN rows would otherwise violate it) — blocks future hand-made non-standard numbers.

T. Migration implications
Replacing the two functions is non-destructive and keeps all vehicles, sequences and the lifecycle lock intact. Sequences continue at car 9 and motorcycle 13. A NOT VALID CHECK does not rewrite existing rows. The unused pool table can stay (empty) for history. Analytics guard (created_at filter) remains harmless but becomes unnecessary for new vehicles. Admin copy and lib/actions/vehicles.ts comments need one small update. This is a production database migration, so it needs Owner approval.

U. Final verdict
**UNSAFE.** The next production CAR create receives QA-PAGN-03. Recommend, before any new vehicle is created: delete the 13 invalid rows from stock_number_pool (data-only, reversible from section E), then schedule policy B (never reuse) with the strict-format guard as the permanent fix. Do not delete or edit the two live QA-PAGN vehicles as part of this; they need a separate Owner decision. Immutable vehicle identity (UUID or a dedicated analytics id) is the later, separate step.
